# LLM、World Model 与 Action Layer 分层方案讨论备忘录

## 1. 背景

当前项目在生存、健康、导航、任务推进等核心决策链路上，默认仍以本地 LLM 作为主要决策中枢；社交聊天链路已经拆分到独立云模型。随着最近几轮排查和实验推进，系统已经暴露出一个较明确的工程特征：

- LLM 在理解上下文、整合记忆、生成对话和归纳动机上表现可用。
- LLM 在长期约束维护、动作格式稳定性、失败后重规划、环境后果预测方面不稳定。
- 仅继续强化 Prompt，已经开始出现边际收益递减。

部门内部有人提出一个典型建议：

- LLM 做理解
- world model 做预测
- action layer / VLA 做行动

本文档用于整理对此建议的技术判断，并给出面向当前项目的适配结论，供后续部门讨论。

---

## 2. 核心结论

### 2.1 总体判断

结论是：**方向正确，但不应机械照搬机器人领域术语。**

对本项目更准确的表述应当是：

- **LLM 负责理解与意图生成**
- **world model 负责可行性与后果预测**
- **action layer 负责动作约束、结构化映射与执行闭环**

不建议继续让单个 LLM 同时承担以下三类职责：

1. 理解当前上下文
2. 预测动作后果
3. 直接输出可执行动作并假定其一定合法

这会使系统在开放表达能力很强的同时，在闭环控制上持续不稳定。

### 2.2 对“纯 LLM 决策”的判断

当前项目的主要问题，不是“LLM 不适合做任何决策”，而是：

**LLM 不适合单独承担状态预测、动作约束和执行校验。**

如果继续把“世界规律理解”“动作可行性判断”“失败回退”“结构化动作生成”全部压在一个 LLM 上，系统容易出现以下问题：

- 因叙事惯性反复选择刚失败过的目标
- 输出格式偶发失控，如异常 `act_address`
- 对失败反馈的优先级维持不稳定
- 长链路后出现状态漂移
- 历史污染信息进入后持续放大

---

## 3. 为什么这个问题已经在项目里出现

最近几轮实际排查已经说明，问题不再是“信息没给够”，而是“系统闭环不稳”。

典型现象包括：

- 导航失败后，LLM 仍可能回跳重试不可达目标
- 某些动作地址被生成成非法格式，触发执行层解析异常
- NPC 聊天 prompt 泄漏会污染记忆，再反向影响后续生成
- 在同一套上下文下，不同模型的行为稳定性和贴题性差异明显

这些现象共同指向一个事实：

**LLM 的语言理解能力可以很强，但它并不天然擅长稳定维护长期可执行约束。**

因此，把“高层理解”和“底层执行闭环”拆开，是合理且必要的。

---

## 4. 如何理解三层分工

### 4.1 LLM：理解与意图生成

LLM 适合承担的职责：

- 解释当前状态
- 整合人物设定、记忆、关系和上下文
- 归纳动机与优先级
- 生成候选策略或候选意图
- 生成社交对话与高层计划

例如：

- “我现在很饿，应该优先补充食物”
- “我刚和 Maria 聊过，当前更适合继续社交还是先休息”
- “在保持人设的前提下，我更倾向于先完成服务职责还是先处理自身生理危机”

### 4.2 World Model：预测与评估

在本项目中，world model 不一定意味着一个大型神经网络模型。更实用的定义是：

**一个能根据当前状态和候选动作，预测其可行性、代价和后果的模块。**

它应当回答的问题包括：

- 当前动作是否可行
- 到达该目标是否有路径
- 执行后会带来什么状态变化
- 是否命中已知失败经验
- 是否与当前关键状态冲突

它的输出不一定是自然语言，可以是结构化评估结果，例如：

```json
{
  "action": "go_to_apple_tree",
  "feasible": false,
  "risk": "high",
  "reason": "target_unreachable",
  "expected_state_delta": {
    "satiety": 0,
    "stamina": -3,
    "health": 0
  }
}
```

### 4.3 Action Layer：约束与执行

Action Layer 的职责不是替代 LLM 思考，而是把自由文本意图安全地落到结构化执行层。

它应当负责：

- 候选动作过滤
- 结构化 action schema 映射
- 地址/对象合法性解析
- 执行前约束检查
- 执行失败后的结构化反馈

换句话说：

- LLM 负责“想做什么”
- Action Layer 负责“允许怎么做”

---

## 5. 对“VLA”概念的项目化判断

如果从机器人或具身智能视角出发，`VLA`（Vision-Language-Action）是一个自然说法。

但对当前项目而言，直接引入这个术语容易造成误解，因为本项目目前是：

- 文本驱动世界
- 明确规则沙盒
- 离散动作空间
- 非真实视觉输入

因此，本项目更需要的不是一个严格意义上的 VLA 大系统，而是一个：

- **结构化动作层**
- **动作约束层**
- **执行闭环层**

也就是说，本项目最合适的落地方向不是：

- “上一个完整 VLA”

而是：

- “建立 LLM 之上的结构化行动中间层”

---

## 6. 对当前项目的适用结论

### 6.1 社交聊天链路

社交聊天本身是开放生成任务，允许一定随机性，适合继续以 LLM 为主。

对这一层的建议是：

- 保留 LLM 主导
- 保留当前的结构校验、中文归一化、污染记忆过滤
- 不要过早把聊天链路改造成强规则系统

原因是：

- 聊天更看重自然性和风格
- 随机性本身是价值的一部分
- 只要结构和污染被控制住，轻微发散是可接受的

### 6.2 生存、健康、移动、任务推进链路

这一层不适合继续采用“纯 LLM 直出执行结果”的方式。

原因是这类任务具有明显特点：

- 有硬约束
- 有可行性边界
- 有明确失败代价
- 有累积状态影响
- 一旦出错，会污染后续多轮决策

因此更适合使用：

- LLM 生成候选意图
- world model 做可行性评估
- action layer 输出结构化执行结果

---

## 7. 推荐的工程分层

结合当前代码架构，建议后续演进为以下五层：

### 7.1 State Compiler

职责：

- 将 `scratch`、记忆、关系、位置、库存、时间、生理状态编译为稳定的结构化输入
- 降低 prompt 中的叙事性噪声
- 让后续 LLM 和预测层面对同一事实源工作

### 7.2 LLM Policy

职责：

- 只生成候选意图，不直接生成原始可执行地址
- 例如输出“去找食物”“优先休息”“去找 Maria 聊天”

### 7.3 World Model

职责：

- 评估候选意图是否可行
- 预测短期后果和风险
- 对失败历史做显式命中检查

### 7.4 Action Resolver / Executor

职责：

- 将候选意图映射到合法目标、合法对象、合法地址
- 输出统一 action schema
- 执行前再做一次硬约束检查

### 7.5 Post-Execution Critic

职责：

- 记录结构化失败原因
- 将失败反馈进入下一轮候选空间过滤
- 防止 LLM 在下一步因叙事惯性立即回跳重试

---

## 8. 为什么这比“继续打磨 Prompt”更有价值

继续打磨 Prompt 仍然有价值，但它更适合解决：

- 语气
- 输出格式提示
- 局部优先级表达
- 少量短链路行为偏差

它不适合单独解决：

- 候选目标空间过大
- 动作合法性问题
- 执行失败回环
- 长期失败反馈优先级衰减
- 世界状态与动作后果预测

因此，Prompt 优化不应停止，但应当从“主解决方案”降级为“辅助解决方案”。

---

## 9. 对当前技术路线的建议排序

从收益优先级看，建议按以下顺序推进：

### 第一优先级：候选动作过滤

先做最小版本的候选空间约束：

- 已知不可达目标本轮禁止再选
- 明显非法对象直接从候选中剔除
- 与当前状态冲突的动作降权或阻断

### 第二优先级：结构化 Action Schema

不要让 LLM 直接自由生成底层执行地址。

应改成：

- LLM 生成意图
- resolver 绑定合法对象、地点、路径

### 第三优先级：轻量 World Model

先做规则驱动或启发式版本，不必一开始就做重型 learned model。

它至少要能输出：

- 是否可行
- 资源是否满足
- 预计收益
- 预计代价
- 是否命中失败经验

### 第四优先级：失败反馈强约束化

从“提示模型失败过”升级到：

- 结构化记录失败原因
- 结构化注入下一轮
- 直接参与候选过滤

### 第五优先级：差异化链路架构

明确拆分：

- 聊天链路：高自由度 LLM
- 生存决策链路：高约束决策系统

## 10. 本地模型与线上模型协同部署议题

除“LLM / world model / action layer”分层外，部门讨论时还应同步纳入另一个现实问题：

**本地部署模型与线上模型应如何配合，以及本地算力建设是否一定比线上更省。**

当前项目已经具备一个初步分层现实：

- 生存、健康、决策等高频链路仍主要使用本地模型
- 社交聊天等复杂生成链路已开始接入线上模型

这条路线并非临时权宜，而是一个值得明确化的长期策略方向。

### 10.1 总体判断

结论是：

- **不建议把“是否本地部署”理解为二选一问题**
- **更合理的方向是本地模型与线上模型协同分工**

原因很简单：

- 本地模型的优势不等于所有任务都适合本地
- 线上模型的优势也不等于所有链路都值得长期走线上
- 真正应当优化的是“单位任务质量 / 延迟 / 成本”的综合比值，而不是单看是否自建机器

### 10.2 为什么“自建算力”未必一定更便宜

很多讨论会默认认为：

- 线上 API 长期按量计费
- 本地机器买断后就更划算

这个判断并不总成立，尤其在当前项目阶段更需要谨慎。

本地部署的真实成本至少包括：

- GPU 采购成本
- 显存冗余成本
- 电费与散热成本
- 故障维护成本
- 驱动、推理框架、量化方案的维护成本
- 多模型并存时的切换与驻留成本
- 团队调参与运维时间成本

如果最终业务形态是：

- 高频但低价值请求很多
- 中低负载长期运行
- 对稳定吞吐要求高

那么本地化通常更有机会摊薄成本。

但如果业务形态是：

- 高质量复杂请求占比高
- 模型更换频繁
- 日调用量并没有大到足以吃满机器
- 需要快速试错不同模型

那么线上 API 反而可能更便宜、更灵活。

### 10.3 对当前项目的现实判断

对当前项目而言，本地与线上的最优边界并不在“模型品牌”，而在“任务类型”。

更适合本地模型的任务：

- 高频、短文本、规则性较强的决策
- 对时延敏感的主循环判断
- 可以接受较小模型能力的状态更新
- 可通过结构化约束降低生成难度的任务

更适合线上模型的任务：

- 社交聊天
- 高质量自然语言生成
- 复杂语义理解和细腻风格控制
- 少量但高价值的关键推理节点
- 需要快速比较不同供应商模型表现的实验链路

换句话说：

- **低成本高频链路更适合本地**
- **高价值高复杂度链路更适合线上**

### 10.4 推荐的协同原则

建议部门统一以下原则：

#### 原则一：按任务价值分层，不按技术偏好分层

不要因为“能本地就一定本地”而强行把复杂任务压到小模型上，也不要因为“线上更强”就让所有请求都走云端。

应优先按任务分类：

- 高频基础判断
- 高风险执行决策
- 高质量社交生成
- 调试/分析/复盘任务

不同任务使用不同模型层，是更符合工程收益的方案。

#### 原则二：本地模型优先承担稳定、可压缩、可约束任务

例如：

- 生理状态判断
- 候选动作初筛
- 简单结构化输出
- 状态摘要与低复杂度分类

这些任务一旦通过 schema、约束和 world model 收口后，不需要超大模型也能稳定运行。

#### 原则三：线上模型优先承担高难度开放生成任务

例如：

- NPC 社交聊天
- 复杂叙事风格生成
- 多人互动语境理解
- 高质量重写、总结、归纳任务

这类任务对语言能力上限更敏感，线上模型的收益通常更明显。

#### 原则四：不要把线上模型当“永久默认”，也不要把本地模型当“政治正确”

模型部署方式应由以下三项共同决定：

- 任务质量要求
- 请求频率与时延要求
- 综合拥有成本

只有同时评估这三项，才有可能得到长期稳定的技术路线。

### 10.5 推荐的项目级部署策略

对当前项目，建议采用“本地常驻 + 线上增强调度”的混合模式。

可以抽象为：

1. **本地常驻层**
   - 负责主循环高频调用
   - 负责结构化判断与低成本推理
   - 保证系统即使离线也能基本运行

2. **线上增强层**
   - 负责聊天、复杂生成、高质量解释
   - 负责实验性模型对比
   - 负责在关键节点拉高输出质量

3. **路由控制层**
   - 按任务类型决定走本地还是线上
   - 按失败率、延迟和成本动态调整默认 provider
   - 为后续 A/B 测试、样本沉淀和成本审计提供统一入口

### 10.6 对后续讨论的建议口径

建议部门在讨论“本地 vs 线上”时，避免陷入以下两个误区：

#### 误区一：买了机器就天然更省

不成立。只有当调用频率、稳定负载和运维能力都足够支撑时，本地化成本优势才会逐步显现。

#### 误区二：线上模型更强，所以都走线上

也不成立。高频主循环如果全部走线上，成本、时延、稳定性和可控性都可能变差。

更合理的表述应是：

**本地与线上不是替代关系，而是分工关系。**

---

## 11. 对部门讨论的建议结论

建议部门讨论时，避免出现两个极端：

### 不建议的极端一：继续让一个 LLM 包打天下

问题：

- 工程不稳定
- 失败代价高
- 很难闭环优化
- 后期越做越依赖 prompt 魔法

### 不建议的极端二：完全取消 LLM 决策权，全部改硬编码

问题：

- 会损失项目最核心的自主性价值
- 会让行为变得机械
- 会削弱社交与开放任务的表现力

### 建议的折中方向

建议采用：

**LLM 主导高层理解与意图，规则化预测层和动作层负责约束与执行。**

这既保留了项目坚持的“LLM 自主性”，又把最容易失控的闭环部分从单一 LLM 身上拆了出去。

---

## 12. 最终结论

一句话总结：

**我赞成“LLM 做理解，world model 做预测，action layer 做执行”这个方向，但在当前项目里，应采用轻量、结构化、规则优先的工程化版本，而不是直接照搬重型 VLA 体系。**

对当前项目最现实、收益最高的路线是：

- 保留 LLM 的高层自主理解能力
- 把世界规律、动作合法性、执行闭环从 LLM 身上拆出来
- 先用轻量 world model 和结构化 action layer 稳住生存决策链路
- 聊天链路继续保留高自由度生成

此外，在模型部署策略上，也不建议简单选择“全本地”或“全线上”。

更合适的路线是：

- 本地模型承担高频、可约束、低成本的基础链路
- 线上模型承担高复杂度、高质量要求的生成链路
- 通过统一路由层进行任务分发、效果对比与成本控制

这条路线既符合项目当前问题形态，也符合后续逐步演进到更强智能体架构的工程路径。
