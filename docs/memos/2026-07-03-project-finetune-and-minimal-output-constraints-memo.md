# 项目定向微调与最小输出约束备忘录

## 背景

在本轮排查中，`Isabella Rodriguez` 出现了一个典型问题：即使 Prompt 已经显式注入了最近一步的失败原因、当前状态、优先级规则，以及“必须想新办法”的强约束，LLM 仍然会偶发性地重复选择刚刚失败过的目标，例如 `apple tree`。

这说明当前系统已经不再是“没有把信息告诉模型”，而是进入了一个更典型的工程阶段：

1. 模型已经拿到了足够的上下文。
2. 模型仍然可能违反约束。
3. 仅继续润色 Prompt，收益会递减。

因此，后续方向需要重新排序：

1. 最小输出约束
2. 日志改造与训练准备
3. 项目定向微调

最新执行计划已单独整理到：

- [2026-07-03-constraint-and-finetune-plan.md](file:///g:/generative_agents/docs/plans/2026-07-03-constraint-and-finetune-plan.md)


## 一、当前结论

### 1. 近期优先级已经调整

当前最紧急的目标不是立刻训练模型，而是先把系统做成“可止血、可观测、可沉淀样本”的状态。

也就是说，当前优先顺序应当是：

1. 用最小输出约束打断明显错误回环
2. 改造日志字段、存储与格式化，建立训练准备契约
3. 建立训练候选样本池
4. 等样本数量与标签完整性达标后，再另开一份模型微调计划


### 2. 为什么不立刻开微调

虽然现有日志已经足够做第一版训练样本种子，但还不适合直接作为高质量、长期可持续的微调数据集。当前主要缺口是：

- 缺少统一的 `decision_id`
- 缺少稳定落盘的 `final_prompt`
- 缺少约束命中日志
- 缺少统一的训练准备日志格式
- 缺少“候选样本”和“最终训练样本”的明确边界

因此，当前更合理的路线是：

- 先做约束层
- 再做日志契约
- 再做候选样本池
- 最后才进入微调


## 二、最小输出约束：当前第一优先级

### 1. 目标

目标不是替 LLM 决策，而是在不夺走决策权的前提下，阻止它输出当前明确违规的结果。

核心原则是：

- 不硬编码“应该去哪里”
- 只硬编码“当前不能再去哪里”

例如：

- 错误做法：如果 `apple tree` 失败，就强制改成 `refrigerator`
- 正确做法：如果 `apple tree` 刚失败，本步禁止再次输出 `apple tree`，其余方案仍交给 LLM 自主选择


### 2. 当前计划中的三层结构

#### 第一层：`InvalidTargets`

在当前 step 内，把最近失败目标明确列成禁选项。

示例概念：

```text
InvalidTargets: apple tree
```

语义：

- 这不是建议
- 是本步不可选的 target 集合


#### 第二层：`Resources` 过滤

把最近失败且不可达的目标从候选资源中拿掉。

这样可以减少模型再次把失败目标当成“正常备选”的概率。


#### 第三层：输出后校验

当 LLM 输出结构化结果后，做一次极小校验：

- 是否命中 `InvalidTargets`
- 是否命中最近失败 target
- 是否与当前关键状态明显冲突

若命中，则：

- 不直接执行
- 触发一次带明确反馈的单次重试

示例反馈语义：

```text
The target apple tree is invalid for this step because it just failed and is currently unreachable.
Choose another feasible immediate target.
```


### 3. 为什么这仍然符合当前架构原则

因为它只排除错误项，不提供正解。

例如：

- 错误：`apple tree`
- 系统只说：这一步不能是 `apple tree`
- 剩下是 `refrigerator`、`behind the cafe counter`、`idle`、`work` 还是别的，仍由 LLM 自己决定

这和硬编码替代行为有本质区别。


## 三、日志改造：当前第二优先级

### 1. 日志改造的目标

日志改造不只是为了排查，而是为了让后续训练样本真正可用、可 join、可审阅。

这一步的目标是为每次决策建立统一的数据契约，至少补齐以下能力：

- 能唯一标识一次决策
- 能还原模型当时看到的最终 prompt
- 能记录是否触发约束
- 能记录最终执行结果
- 能让多份日志稳定关联


### 2. 需要补齐的核心字段

当前计划里，训练准备日志至少需要有：

- `decision_id`
- `persona`
- `curr_step`
- `prompt_kind`
- `final_prompt`
- `prompt_hash`
- `decision`
- `constraint_hit`
- `retry_reason`
- `execution_outcome`

这些字段会统一写入新的训练准备日志，而不是继续分散在多份难以稳定 join 的 JSONL 文件里。


### 3. 新的存储思路

当前建议的目录与职责划分如下：

- `docs/`
  - 放备忘录、工作流说明、设计文档
- `docs/plans/`
  - 放正式执行计划
- `test/`
  - 放 `test_` / `check_` 测试与离线检查脚本
- `reverie/backend_server/persona/training/`
  - 放训练准备相关的构造器和样本池逻辑
- `logs/training_dataset/decision_training_prep.jsonl`
  - 放统一格式的训练准备日志
- `logs/training_dataset/decision_training_prep.jsonl`
  - 放统一格式的训练准备日志
- `logs/training_dataset/training_candidates.jsonl`
  - 放待审阅的训练候选样本池


### 4. 日志格式化规则

后续训练准备日志应尽量遵循这些规则：

- 一行一个事件
- 必带 `decision_id`, `persona`, `curr_step`, `event`, `ts`
- 复杂对象使用 JSON 对象，不拼接自然语言长字符串
- 同一次决策的多条事件依靠 `decision_id` 聚合
- 候选样本抽取优先从统一训练准备日志读取，而不是直接拼装多份旧日志


## 四、训练准备：先建候选样本池，不直接开训

### 1. 当前阶段的真实目标

当前阶段不是立即产出最终的 `SFT` 或偏好训练集，而是先建立一个“训练候选样本池”。

原因很简单：

- 现有日志可以识别很多错误输出
- 但不是每条错误都天然有唯一标准答案
- 如果直接拿去训练，容易把弱标签、脏标签和偶发事件一并喂给模型

因此更稳妥的做法是：

1. 先从日志提取候选样本
2. 标记 `review_status`
3. 人审或规则审通过后，再进入最终训练集


### 2. 候选样本池应该长什么样

建议先沉淀类似如下结构：

```json
{
  "decision_id": "Isabella-61-abc123",
  "persona": "Isabella Rodriguez",
  "final_prompt": "Decision Capsule: ...",
  "rejected_output": "Gather apple tree",
  "execution_outcome": "path_not_found",
  "review_status": "pending"
}
```

这里最关键的是：

- 它是候选样本，不是最终训练样本
- 它允许先收集，再审阅


### 3. 当前优先收集哪些候选样本

建议优先沉淀三类：

#### A. 失败纠偏样本

输入特征：

- `navigation_failure` 存在
- 最近失败目标明确
- 当前库存和生理值说明没有必要继续原动作

错误输出：

- 继续选择同一个失败 target


#### B. 生理约束样本

输入特征：

- `satiety < 30 and inventory empty`
- 或 `stamina < 30`

错误现象：

- 被长期角色叙事带偏


#### C. 动作收敛样本

输入特征：

- 刚失败过
- 刚完成一个阶段动作
- 已经处于高库存/高饱食度

错误现象：

- 不断重复旧意图


## 五、项目定向微调：现在是后置阶段

### 1. 微调仍然重要，但不是当前立刻执行项

项目定向微调仍然是中长期非常重要的方向，目标也没有变化：

- `latest failure > long-term goal`
- `current feasibility > role narrative`
- `high inventory + high satiety -> avoid repeated gather`
- `unreachable target -> immediate replan`
- `current local feasible option > distant story-consistent option`

但它的启动前提已经明确后移：

- 先有稳定的约束层
- 先有统一的日志契约
- 先有足够多、足够完整的候选样本
- 先通过 readiness gate


### 2. readiness gate 的意义

后续只有当以下条件大致达标时，才应该进入新的“模型微调实施计划”：

- 至少 500 条带 `decision_id` 的完整候选样本
- 至少 100 条 `navigation_failure` 纠偏案例
- 至少 100 条 `high inventory + high satiety` 错误案例
- 至少 90% 样本包含 `final_prompt`
- 至少 90% 样本包含 `execution_outcome`
- 至少 80% 样本完成人工或规则审校

也就是说，当前这份备忘录不再把“微调”写成下一步直接执行，而是写成“样本与契约达标后的下一阶段工程”。


## 六、为什么新的顺序更合理

### 1. 更符合当前问题的本质

当前最大的问题不是“模型完全不会”，而是：

- 会偶发违约
- 当前日志还不够像训练数据产品

所以先修“错误回环”和“数据契约”，比直接开训更稳。


### 2. 更符合当前项目原则

本项目已经形成了清晰原则：

- 程序负责给出物理事实
- LLM 负责自主选择下一步
- 不要用硬编码替代 LLM 的主观判断

在这个原则下：

- 最小输出约束是“只拦截确定错误项，不替它决定正解”
- 日志契约是“为后续学习做数据准备”
- 定向微调是“在数据成熟后提升默认决策质量”

这个顺序比“先训再说”更符合现有架构哲学。


### 3. 更符合工程可控性

如果现在直接做微调，会同时面对三类不确定性：

- 约束层还没稳定
- 日志字段还不完整
- 样本标签质量还不均匀

而改成新的顺序后，系统会更可控：

1. 先打断最明显的错误回环
2. 再让日志具备训练准备能力
3. 再沉淀候选样本池
4. 最后才开启模型微调


## 七、当前建议的结论

基于目前的排查结果和新的计划结构，可以得出如下判断：

1. 仅继续润色 Prompt，收益已经开始递减。
2. 当前问题已经明确包含 LLM 违约输出。
3. 最小输出约束是近期第一优先级。
4. 日志字段、存储、格式化改造是第二优先级。
5. 项目定向微调仍然重要，但必须后置到样本准备成熟之后。


## 八、一句话总结

如果把当前系统比作一个会偶发犯错的 NPC 决策器，那么新的工程顺序是：

- 先给它一个最小但可靠的防撞栏
- 再把它每次犯错和纠错的过程完整记录下来
- 再把这些记录沉淀成可审阅的候选样本池
- 最后才用足够多的高质量样本去训练它“平时更懂这个世界该怎么活”
